The process · how a cycle works 2 / 23
One cycle, six months

Four moves per pairing.

01 · COACH

Pick a reviewer one rank above

App suggests top 5 candidates passing the cross-project hard rules. Coach agrees the pairing in Slack/email, then records it in the app.

›
02 · BOTH

Schedule the session

1–1.5 hour slot, agreed by both. MVP records a date. Phase 2 picks from Google freebusy and creates the calendar event.

03 · BOTH

Share practices, not just code

Architecture & patterns · clean code · testing/observability/security · AI workflow. Reviewer shows what one rung up looks like across these.

›
04 · BOTH

Short feedback, both directions

Reviewer fills four weighted sections + wrap-up. Reviewee notes top thing learned, what they'll try in two weeks, and which topics were covered.

The rules · matching & auto-assignment 3 / 23
Cross-project means cross-project

Hard rules every pairing must pass, soft signals that rank.

Hard rules · all must pass

✓
Different project
Same project = within-project review. Not what this is.
✓
Different coach
Sharing a coach = sharing management context. Cleanest outside eyes.
✓
No prior pair in 2 cycles
Repeat pairings rarely add new perspective.
✓
Reviewer rank strictly higher
On the 9-cell maturity grid. Exposure is the point.
✓
Reviewer below load cap
≤ 2 active assignments per cycle.

Soft signals · rank among eligible

+1
Different tech stack
.NET ↔ Python on event sourcing is the whole point.
+1
Different BG
Cross-BG architecture perspectives.
+2
Rank gap of one
Closer rank transfers better than a chasm.
+1
Lower current load
Per slot free. Spreads work evenly.
↓
Re-validated at recording
Hard filter runs again at submit; rejects with reason.
